# 06 — Donante real: BSP MT6877 6.6 de Samsung A34

## Qué existe

`Fede2782/android_kernel_samsung_a34x`, rama `sep-17.0/stock`, público:

```
kernel-6.6/                     ACK 6.6.82
kernel/kernel_device_modules-6.6/  BSP MediaTek MT6877 (overlay)
vendor/mediatek/kernel_modules/    módulos de vendor
build_kernel.sh                 build Bazel/Kleaf con overlays
```

El A34 5G usa el mismo SoC (Dimensity 1080 / MT6877V). El BSP contiene:

- `drivers/clk/mediatek` con `COMMON_CLK_MT6877*`
- `PINCTRL_MT6877`
- `mt6359p` (MFD, regulator, accdet)
- `drivers/gpu/drm/mediatek/mediatek_v2/mtk_dsi.c`
- `focaltech` touch
- `CHARGER_BQ25601`, `MTK_LPM_MT6877`, `SND_SOC_MT6877`
- `arch/arm64/boot/dts/mediatek/a34x/` y `ap_mtk_mt6877.dtsi`

## Cobertura medida contra ruby

Cruzando `configs/ruby_defconfig` con los Kconfig del BSP:

| Métrica | Valor |
|---|---|
| Opciones `=y` de ruby ausentes en ACK 6.6.127 | **302** |
| De esas, declaradas en el BSP del A34 | **181** |
| Sin declarar (renombradas o específicas de ruby) | 121 |
| Headers del build real ausentes en ACK | 183 |
| De esos, presentes en el BSP | 40 (el resto son `generated/asm/*` de cualquier build) |

Las 121 restantes incluyen lo verdaderamente Xiaomi/ruby:

```
MI_DISP, MI_DISP_*, MI_HARDWARE_ID
DRM_PANEL_M16_36_02_0B_DSC_VDO, ..._42_0D_0A..., ..._45_02_0C...
FPC_FINGERPRINT, GOODIX_CAP_FINGERPRINT, INPUT_AW8697_HAPTIC
CHARGER_MM8013, CHARGER_SGM41511
```

Esos no están en el BSP del A34; sí están (en versión 4.19) en
`RubyxLabs/kernel_xiaomi_mt6877`. Portarlos a 6.6 es el trabajo real, sobre
todo `MI_DISP` y los paneles M16.

## Diferencias que hay que resolver

1. **Versión**: BSP 6.6.82 vs ruby 6.6.127. Son 45 parches estables; el código
   MTK suele aplicar con fuzz, pero hay que revisar `task_struct`,
   `struct device`, DRM y VFS.
2. **`=m` vs `=y`**: el A34 compila los drivers MTK como módulos
   (`CONFIG_PINCTRL_MT6877=m`, `COMMON_CLK_MT6877=m`). ruby los lleva
   built-in. Compilarlos `=y` requiere revisar `module_init`/`late_initcall`,
   dependencias y orden de probe; no es solo cambiar la letra.
3. **DTS**: no reutilizar el del A34. Usar
   `extracted/device/fdt-live-labeled.dts` (el de ruby, ya con etiquetas) y
   los `cust_mt6877_*` del BSP solo como referencia de bindings.
4. **Build**: el A34 usa `build_kernel.sh` + Kleaf/Bazel y varios overlays
   (`mt6877_overlay.config`, `mt6877_teegris_5_overlay.config`). ruby se
   compila con el sistema clásico de Lineage (`TARGET_KERNEL_SOURCE`). Hay que
   elegir uno y mantener el `vermagic`.
